Design Principles

Six rules that decide every layout, every sentence of copy, every animation.

01
Show the work
Every figure on screen links to the calculation or document that produced it.
02
The model never computes
Math is deterministic and code-owned. Language explains; it never derives a number.
03
Confidence has boundaries
Every recommendation states what would change it. Certainty is never implied past its evidence.
04
One recommendation, ranked
A single top action, with alternatives visible but visually subordinate. Never a wall of options.
05
Plain language over jargon
Clarity is a feature. If a term needs a tooltip, prefer the sentence that doesn’t need one.
06
Calm, not clever
No countdowns, no urgency copy, no gamified streaks. Money decisions deserve a steady interface.
Voice & tone
Confident. Analytical. Transparent. Never hype. Declarative sentences, cited numbers, no exclamation marks, no emoji.
Avoid“Grow your wealth!”
Use“Understand every financial decision before you make it.”
03

Design System

This is not a component inventory. It is the interaction language of NextRupee — a small set of reusable patterns, each justified by a decision it supports, not a widget it resembles.

A generic form asks for data. NextRupee asks for a decision, previews its consequence, and remembers why it was made — that difference is the entire system.

The Interaction Language
Decision Selector
Why it exists: some choices aren’t settings — picking “medium risk” changes the math downstream. A dropdown hides that stakes; a Decision Selector previews the consequence (the exact allocation split) beside each option before it’s chosen. Removes: the guesswork of what a label like “medium” actually means for your money.
Ranked Action List
Why it exists: a wall of equal-weight options forces the user to re-rank recommendations themselves. This pattern renders one action as visually dominant and every alternative as deliberately subordinate, collapsed until asked for. Removes: decision paralysis from comparing options the system has already ranked for you.
Evidence Trace
Why it exists: a number without a source asks for blind trust. Every claim sits directly above a monospace reference to the calculation or document that produced it — always visible, never a hidden tooltip. Removes: the need to take the system’s word for it.
Confidence Signal
Why it exists: not a decorative status pill — a stated claim about how much weight this recommendation deserves, and a link to exactly what would lower it. Removes: false certainty; the interface never implies more confidence than the evidence supports.
Progressive Commitment Flow
Why it exists: a 16-question form feels infinite. This pattern reveals one small, low-stakes topic at a time and silently skips branches that don’t apply — the user is never shown a question with no bearing on their situation. Removes: the fatigue of a form whose length you can’t estimate.
Reasoning Disclosure
Why it exists: not a generic FAQ collapse — a fixed cascade (Decision → Evidence → Reasoning → Alternatives → Risks → Assumptions → What would change this) that answers “why?” completely, in the same order, every time. Removes: the need to ask a follow-up question — the follow-up is already open.
Financial Input Patterns

Not text fields, dropdowns, or checkboxes with financial labels stuck on — each pattern below is shaped by the kind of financial decision it captures.

Currency Input
Purpose — capture rupee amounts with zero ambiguity about scale.
When — income, expenses, loan amounts, contributions.
Behavior — auto-formats with Indian digit grouping (1,00,000) live; right-aligned monospace digits so amounts compare visually.
Validation — rejects negatives inline; magnitudes far outside plausible range prompt confirmation, not a block.
Mobile — numeric keypad only; no paise unless the field is naturally sub-₹1,000.
Accessibility — label states the unit for screen readers (“Monthly income in rupees”), not just a ₹ glyph.
Percentage Input
Purpose — capture rates whose meaning changes at a threshold.
When — loan APR, expected-return overrides.
Behavior — stepper + type-in at 0.1% increments; shows the value against its reference line live (“9.0% — below the 10% prepay threshold”).
Validation — values outside 0–40% require confirmation before accepting.
Mobile — 44px stepper targets; keypad allows one decimal point only.
Accessibility — threshold comparison is read as text, never conveyed by color alone.
Single-Choice Cards
Purpose — choose among 2–4 mutually exclusive framings that carry real downstream consequence.
When — risk tolerance, investment horizon.
Behavior — full-width tappable cards, each showing its own consequence line before it’s selected.
Validation — one selection required; no default pre-selected on consequential choices.
Mobile — stacked, 56px minimum height per card.
Accessibility — selection shown by border + icon + aria-pressed, never color alone.
Goal Selection Chips
Purpose — name what money is for without a blank text field.
When — onboarding goal capture, one or many.
Behavior — tapping a chip immediately asks for the one number that matters next (timeline), not a full form.
Validation — at least one goal required; “Other” opens a 40-character field.
Mobile — wraps to 2 rows max; labels never truncate.
Accessibility — role="checkbox" per chip with a visible focus ring and group legend.
Risk Preference Selector
Purpose — translate a feeling into the allocation hierarchy’s three tiers.
When — once at assessment; revisited only on a flagged life event.
Behavior — three plain-language statements, not a numeric slider — sliders imply false precision for something qualitative.
Validation — the choice maps directly to a fixed split, previewed beneath it.
Mobile — full-width stacked, single-select.
Accessibility — full sentences read cleanly by screen readers, never “Low/Medium/High” alone.
Binary Decision Cards
Purpose — capture a yes/no fact that gates a rule, never buried in a list of many checkboxes.
When — dependents, existing insurance — any answer that flips a rules-engine branch.
Behavior — two large side-by-side cards, each restating the stakes of that answer in one line.
Validation — required before advancing; no default.
Mobile — stacks only below 340px width.
Accessibility — role="radiogroup" with a full accessible name per card.
Progressive Multi-Step Form
Purpose — turn a long assessment into a series of small, low-stakes decisions.
When — profile assessment; any flow past 3 fields.
Behavior — one topic per step (2–3 related questions); adaptive skip logic removes irrelevant branches silently.
Validation — inline per field; a step can’t advance with a required field empty.
Mobile — Next/Back bar pinned to the bottom, one-handed reachable.
Accessibility — step change announced via aria-live; focus moves to the new step’s first field.
Financial Summary Card
Purpose — let the user confirm their numbers feel right before the system reasons over them.
When — end of assessment, or anywhere multiple entered values need a joint sanity check.
Behavior — restates entries as a short narrative sentence plus a compact table, not a raw field dump.
Validation — read-only; edits route back to the originating step.
Mobile — sections collapse past 4 line items.
Accessibility — table uses proper th scope for row/column navigation.
Inline Guidance
Purpose — answer “is this good or bad?” the instant a number is entered.
When — any field whose meaning depends on a threshold.
Behavior — a one-line, non-modal note appears the moment a threshold is crossed; disappears if the value moves back.
Validation — never blocks submission — guidance, not gatekeeping.
Mobile — wraps beneath the field, never a tap-and-hold tooltip.
Accessibility — announced via aria-live="polite" so it doesn’t interrupt typing.
Validation & Error States
Purpose — prevent bad data from reaching the rules engine without shaming the user.
When — any field with a hard constraint.
Behavior — errors stated as fact (“Enter an amount above ₹0”), inline below the field, icon + text — never red alone.
Validation — blocks only on hard constraints; soft anomalies use Inline Guidance instead.
Mobile — the form scrolls the errored field above the keyboard, never clipped.
Accessibility — aria-invalid + aria-describedby link field to error text.
Progress Indicator
Purpose — make the assessment’s length legible so it never feels open-ended.
When — any flow past 2 steps.
Behavior — step count (“Step 4 of 8”) paired with a filled bar — count alone hides pace, bar alone hides remaining steps.
Validation — n/a.
Mobile — sits above the step title, always in view without scrolling.
Accessibility — progress conveyed as text, not bar width alone.
Review & Confirmation
Purpose — an explicit checkpoint before the rules engine runs, not a silent auto-submit.
When — end of assessment, or before any lasting action (e.g. resetting a profile).
Behavior — states what happens next in one sentence, plus a single confirm action — no competing secondary actions beside it.
Validation — n/a — only confirms already-validated data.
Mobile — confirm button full-width, thumb-reachable.
Accessibility — descriptive button label (“Generate my recommendations”), not just “Confirm”.
LAYOUT
12-col grid, 1280px max, single-column below 640px.
ACCESSIBILITY
WCAG AA contrast minimum; 44px touch targets; never color-only status.
MOBILE-FIRST
Design the 390px frame first; expand, don’t shrink.
ANIMATION
160–220ms ease-out; motion clarifies state, never decorates.

AI Intelligence Engine

The interface only works if the system behind it is trustworthy. Two rules make that visible in the UI itself.

RULE 01
The rules engine owns every number
Deterministic Python computes runway, debt-service ratio and allocation splits. Same profile in, same ranking out — the language model only narrates a result it did not produce.
RULE 02
Every claim is schema-validated
Each recommendation fills a fixed structure — decision, evidence, confidence, invalidators, alternatives. A claim with no citation is rejected before it reaches the screen.
The NBCA card, structurally
action · category · amount_range · rationale_chain · evidence[] · confidence · invalidation_conditions[] · alternatives[] · opportunity_cost
Gold Engine
Live data feeds + a ~30-node driver graph
Retrieval
Graph lookup, then vector search — not generic RAG
Guardrails
Blocks instrument-specific claims; regenerates on mismatch
Freshness
Data >7 days stale caps confidence at medium
